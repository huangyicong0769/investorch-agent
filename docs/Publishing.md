# Maintainer release procedure

This guide covers release review, GitHub release assets and protected PyPI
publication through a Trusted Publisher.

## Configure publication before the first release

A maintainer with the required external permissions must:

1. Verify ownership of the `investorch` project name on PyPI. For an existing
   project, add a Trusted Publisher in its **Publishing** settings. For a new
   project, configure a pending publisher under the PyPI account's publishing
   settings; the first successful upload creates the project.
2. Configure that publisher with owner `huangyicong0769`, repository
   `investorch-agent`, workflow filename `publish.yml` and environment `pypi`.
   These values must match exactly. No PyPI API token is required.
3. Create the repository's GitHub environment named `pypi`, require a maintainer
   reviewer, prevent self-review where available, and allow deployment from
   release tags matching `v*.*.*`. Verify that the repository's GitHub plan
   supports and enforces these protection rules. Restrict tag creation through
   the repository's rulesets as appropriate.

See the official PyPI instructions for [existing projects](https://docs.pypi.org/trusted-publishers/adding-a-publisher/),
[new projects](https://docs.pypi.org/trusted-publishers/creating-a-project-through-oidc/)
and [Trusted Publishing](https://docs.pypi.org/trusted-publishers/using-a-publisher/).

## Review and release

1. Complete and review the release branch, its dependency changes, real
   application checks and the wheel and source installation checks.
   Keep `pyproject.toml` and `frontend/package.json` versions aligned, include
   both language release notes under `docs/releases/`, and run
   `uv run --no-project python scripts/check_release.py --tag v0.3.0`.
2. Obtain explicit approval before merging to `main`, creating/pushing the
   `v0.3.0` tag or publishing. Run the full CI gates on the approved commit.
3. Push the approved tag on a commit contained in `main`. The `Release` workflow
   validates the tag, runs quality/package checks and creates a **draft
   prerelease** with a wheel, source distribution and `SHA256SUMS`.
4. Inspect that draft and its workflow results. After final release approval,
   clear the prerelease flag and publish the GitHub release as a stable release.
   Publish it with the GitHub UI or a maintainer credential; events generated by
   a workflow's `GITHUB_TOKEN` do not trigger another workflow.
5. The `Publish to PyPI` workflow reacts to a stable release's `published` event.
   It validates the tag/version/notes and membership in `main`, builds the wheel
   and source distribution, and checks fresh installations
   outside the checkout. It transfers those exact qualified files to a separate
   publishing job. Approve that job in the protected `pypi` environment after
   reviewing its build result. Only that job receives OIDC permission; it checks
   out no source and uses PyPA's publish action with attestations enabled.
6. Verify the workflow result, PyPI version/files/attestations and a fresh
   installation of `investorch==0.3.0` before marking publication complete.

Drafts and prereleases do not publish to PyPI. There is no manual publish trigger.
Publish the draft directly as stable: promoting an already published prerelease
may produce a different release event and does not match this workflow's trigger.
If a run fails before upload, fix the issue and rerun the failed workflow after
review. If PyPI has accepted any files, inspect the remote files before retrying;
the workflow does not skip existing files, and PyPI versions cannot be replaced.

The GitHub draft and PyPI jobs build separately; each publishes the artifacts
qualified in its own run. The GitHub `SHA256SUMS` describes its release assets.
See [Upgrade](Upgrade.md) for user configuration migration.

The job separation follows the [PyPA publishing action guidance](https://github.com/pypa/gh-action-pypi-publish);
release trigger behavior is documented by [GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#release).
