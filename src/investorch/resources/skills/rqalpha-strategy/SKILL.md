# RQAlpha strategy workflow

Choose the entry point that serves the current request. For report consistency, compare claims with their cited tables and return supported corrections. For execution validation, inspect saved requests, source snapshots and behavior artifacts. New or rerun studies follow preparation through execution. A continuation begins by recovering the effective study definition and resolving choices that need the user.

1. For authoring, modifying or running a strategy, read `references/runtime.md` in full. Before executing the first comparison or parameter grid, also read `references/examples.md` for the complete workflow, supplied strategy fixtures and result verification. A review uses the reference sections needed for the requested check.
2. Record the study definition: universe and membership dates, period, signal horizon and observation clock, signal cutoff, rebalance and exit schedule, target allocation, initial capital and benchmark. For a continuation, reconcile prior decisions and source artifacts with the current request. When definitions conflict, explain the alternatives and their effect, ask the user to choose, and continue preparation that is independent of that choice. Identify the intended variable in a comparison and keep the remaining definitions shared across cases.
3. Read relevant `backtest.*` defaults with `get_config` and the supported per-run controls in the runtime reference. Use dotted leaf keys or `get_config(key=null)`. Pass study-specific execution assumptions through `run_backtest.parameters`; null fields inherit AppConfig defaults, while explicit false and zero override them. Preserve current costs unless the user requests a change. Changes to future application defaults follow the configuration workflow.
4. In native mode, call `inspect_rqalpha_data` for the actual instruments, benchmark and necessary signal warm-up. Confirm each observed bar range. In overlay mode, follow the overlay contract in the runtime reference and use coverage errors returned by `run_backtest`. Use available MCP query tools for research inputs such as historical index membership, carrying returned symbols and effective dates into a Workspace input artifact. Establish backtest price coverage separately from research-source availability. If required membership inputs are unavailable, present the missing input and the effect of a proposed replacement to the user.
5. Use `explore` and `edit` to prepare ordinary Workspace RQAlpha strategy files. Check their signal window, cutoff and actual-position exit logic against the recorded definition. An L-exchange-trading-day return uses L+1 completed closes with `skip_suspended=False`; a non-suspended-observation horizon is a separate definition. The strategy owns signals and orders; the runner owns costs, matching, holdings evolution and execution policy. Use `exec_command` for file preparation, syntax/pure-calculation checks, statistics and plots.
6. Call `run_backtest` through normal approval for a representative small run. Verify provenance, independently computed signals and actual holdings against the study definition before expanding. Execute each required case through a separate function-tool call. Stage large matrices into bounded groups, and report meaningful findings and remaining work at stage transitions.
7. Build a comparison table from verified saved requests, strategy snapshots, summaries and relevant tables. Include run identity, effective parameters, strategy logic version, input identity and completion status. Reconcile the returned `runtime` with `request.json.runtime`. After a logic fix, rerun all affected comparison cases using the corrected logic; explain parameterized source differences against the intended variable. Verify target versus actual holdings and exposure, including blocked exits.
8. Use one metric definition and boundary per comparison column. State formula, unit, interval, annualization factor and initial NAV; include the first observed day's return. Keep CAGR difference in percentage points separate from geometric annual relative return in percent. Check each narrative claim against the complete comparison table, then write the report. Apply the Memory workflow when the result establishes durable project context. Mark work complete from these verified outputs and identify remaining cases.

## Diagnose and continue

- On a restricted host-directory error, use the built-in inspection and execution tools for their owned capabilities.
- On missing instruments, warm-up or coverage, retain the exact symbols, interval and returned diagnostic. Present the missing input and the research effect of changing the universe, interval, source or engine; ask the user to resolve a required change to the formal study.
- On a strategy exception, use its safe diagnostic and source location to repair the identified expression, then rerun the same representative case with the agreed definition.
- For engine or data failures, retain the failed call and its diagnostic. Isolate a suspected symbol or period in a separately named diagnostic variant, recording its difference and purpose. Keep the formal study's original definition and blocked status while investigating. A generic error establishes a missing diagnostic; explain that gap and request the information or decision needed to continue.
- Finish a comparison with traceable `run_backtest` results for the claimed cases, verified artifacts and conclusions scoped to the observed sample. Record untested cases and their current blockers alongside completed results. Backtest evidence establishes simulated behavior; live execution follows its own workflow.
